# Blog kit diagram system

The design system for diagrams in Mark's technical blog posts, and everything used to build it: the OpenPencil design file, the lab that generates and checks the diagrams, the SVGs placed in the design file, and this record. It starts with the blog and will later grow into the wider design system (with design-docs). Everything here was decided interactively with Mark.

The technical-blog skill carries a portable copy of the decided system for agents writing posts: `skills/active/technical-blog/references/diagram-system.md`, `scripts/pele-post.mjs` and `scripts/overlap-check.js`. This folder is the source; when a rule changes here, update the skill's copy too.

## How this record is written

- **Principles** say what we're trying to convey; use judgement where they apply. **Rules** are explicit defaults and guardrails, followed as written. Rules exist because models don't always follow a principle closely; add one where a model keeps drifting or a scenario needs to be pinned down.
- When Mark reacts to a specific case, record the principle behind it, not just the fix, so the answer carries over to every diagram type.
- **Every change gets an explainer page** (Mark, 2026-10-24): an HTML page with a section per change (what, why, where it lives, the overlap-check result) and the diagram before and after, as inline SVG built from the skill alone. "Before" reproduces the old behaviour by switching the change off. Publish it to the artifact share. The first one is `scratch/2026-10-24-changes-notes/build.mjs`; copy its shape.
- **The guide doesn't prescribe layouts.** It covers style, meaning and spacing; how to arrange a diagram (stacked or side by side, which direction) is the writer's call (Mark, 2026-10-24, declining a "prefer stacked regions" rule after the Sonnet/Opus comparison). Source patterns that exist to stop a known crowding problem are the exception.

### Working in the lab

- Install the pinned icon packs once: `cd lab && pnpm install --ignore-workspace`. The lab sits outside the repo's pnpm workspace on purpose.
- Render Mermaid with the pele skill: `node <pele skill>/scripts/render.mjs types/flow.mmd -o types/flow.svg`. The bar chart is rendered with `-w 692` (see Layout).

## Driving OpenPencil

- The app runs on Windows; its MCP server is the WSL systemd service `openpencil-mcp.service` (`docs/openpencil-mcp-wsl.md`). It writes the discovery file the app reads, and WSL forwards the app's connection to it. Start the service before the app. Don't install `@open-pencil/mcp` on Windows too: the app starts it, and the two servers overwrite each other's discovery file.
- CLI from WSL: `openpencil …`. The base `.zshrc` exports `OPENPENCIL_MCP_DISCOVERY_PATH`, which is how the CLI finds the service. A shell that doesn't load `.zshrc` (an agent's Bash tool) needs it exported first: `export OPENPENCIL_MCP_DISCOVERY_PATH=$(zsh -ic 'print -r -- $OPENPENCIL_MCP_DISCOVERY_PATH')`.
- Open the design file by its UNC path; a Linux path makes the app save to `C:\home\…`. `documents open` resolves its argument as a Linux path, so send the UNC path as an `open_file` RPC: `curl --unix-socket /run/user/1000/openpencil/mcp.sock -H 'Content-Type: application/json' --data '{"command":"open_file","args":{"path":"\\\\wsl.localhost\\Ubuntu\\home\\mark\\workspace\\repos\\mfz-home\\design\\blog-kit\\blog-kit.fig"}}' http://localhost/rpc`.
- Each CLI call is a fresh session: `switch_page` does not persist, and `render` lands on the app's current page (move it with `reparent_node`). Pass `--page-id`; node searches cover only that page, and other pages report 0 nodes until the app loads them. Node ids change when the file is reopened, so look nodes up by name.
- `<Span>` in render JSX ignores `bind`; use a literal `color`.

### Diagrams go in as editable vectors

The house style is page CSS, which `import_svg` can't read, so diagrams are baked first:

Lab pages load `pen.js`, which draws as the page loads, so a bake carries the pen (the Diagrams page and `svg/` were re-baked with it on 2026-10-24): plain stroked paths and hatching lines, which import as editable vectors (tested 2026-10-24; round line ends come in flat).

1. `node lab/bake.mjs <page.html> <out-dir> <figure-id>[@<w>x<h>]…` copies each element's computed style onto the SVG, draws the paper as dots or lines (read from the figure's background, at its spacing), turns `#lasso` loops into wobbly paths (OpenPencil drops SVG filters), flattens nested `<svg>` icons into transformed groups (the importer ignores an inner viewport's x/y/viewBox), and drops shapes with neither fill nor stroke (the importer fills them black). `@<w>x<h>` grows the paper to that aspect with the diagram centred, to fill a fixed slot. `@<w>` widens the paper to that width at full scale; the Diagrams page uses `@720` for Types cards, so each diagram shows at its real size in an article-width card. Cards hug their content, so a re-baked diagram of a new height never spills out.
2. `node lab/place.mjs <baked.svg> <name> <page-id> <x> <y> [replace-id]` imports it, clears the white fill the importer gives the frame (it showed at the paper's rounded corners), and restores dashes, which `import_svg` drops. They go on each stroke: the node-level `dashPattern` is never drawn (0.16.0).
3. `node lab/swap.mjs <baked.svg> <node-id> <name> <page-id>` replaces a node in place, scaled to its width.

Style meant to survive the import must be a real fill or stroke; a stroke on text is ignored. `lab/anatomy.mjs` builds the spacing anatomy: it measures the S1 sequence on its lab page (once Kalam has loaded) and lays numbered orange measurement bands over the baked SVG.

## Principles (why)

1. **Colour follows the message.** Colour only what the diagram's one sentence is about. If a reader can't say why something is coloured, it is neutral.
2. **Exact layout, a human hand.** Pele places every box, line and label exactly; the pen draws them with a light hand, and personality lives in group loops, handwritten labels and notes, hatching on the focus, and paper. That is how the diagrams stay cute and still work-appropriate.
3. **Icons over subtitles.** A known service is recognised by its icon; a subtitle is only for something the icon can't say.
4. **Nothing touches.** Text, lines and outlines keep clear space between them.
5. **Contrast shows the subject.** One thing against the rest: that one stands out and everything else stays quiet. When the whole set is the subject, the whole set carries the colour.
6. **Fix the source, not the symptom.** When Pele's layout crowds something, change the Mermaid source first; post-process only repeat offenders.

## Rules (what) — Decided

### Colour system

Colour is attention: spend it on what the diagram is saying, not on what kind of element something is (Mark, 2026-10-24, after the Sonnet review). This replaced rules keyed to element types ("groups get hues", "one focal element", "status only when literal").

**Principles**

1. **Colour follows the message.** Write the diagram's one sentence first, then colour only what it is about. Any element can carry colour: a box, a group, a `loop` frame, a line, a bar, a point. A loop is coloured when "this repeats for everything" is part of the point.
2. **Neutral is the default; colour is a small budget.** Every coloured element answers "why is this coloured?" with something the text says. No colour all over the place.
3. **Emphasis matches the comparison.** One against the rest: one pink, the rest neutral. The whole set is the subject: colour the whole set. No single subject: no pink.
4. **A colour means the same thing in every post.**

**Roles**

| Role | Colours (Dracula) | Means |
|---|---|---|
| Neutral | fg `#f8f8f2`, muted `#a3a8c3`, line `#c6c8d8`, outline `color-mix(muted 60%, bg)` | everything not being pointed at |
| Emphasis | pink `#ff79c6` | what this diagram is about |
| Grouping | cyan `#8be9fd` → purple `#bd93f9` → yellow `#f1fa8c` | these belong together, when membership matters to the point |
| Status | green `#50fa7b`, orange `#ffb86c`, red `#ff5555` | a state the reader needs: done / added / ok, in progress / warning, failed / removed / at risk |

**Rules**

- Every box, line and label starts neutral; colour is added per diagram by `data-id`, never by changing the defaults.
- Colour goes on outlines, text, loops, lines and markers. The only fill is the 14% pink tint on an emphasised box or point. Never colour large areas (group backgrounds, gantt section bands, quadrants): borderless tinted fills read as muddy on dark (Mark disliked Soft pastel).
- Pink is only ever emphasis: never a group, a status or decoration.
- Grouping hues go in order, at most three. Items inside a coloured group stay neutral (Mark: strange when the group and everything in it share a colour).
- A status colour marks a real state and means one state throughout a diagram. Done tasks in green are fine when "what's done and what's left" is the point.
- More than three colours besides neutral means the diagram is saying two things.
- **"Not used" is not a status.** Draw it neutral and dashed, not red.
- Icons are never coloured; group icons sit on the paper in muted, service icons on a light tile.
- Colour text with `fill`, never `stroke`.
- Types without the usual boxes start neutral: gantt tasks and milestones outlined, no section bands; quadrants outlined, no fills; chart bars and points neutral; mindmap branches and timeline periods neutral; git main neutral, other branches in grouping hues, outlined pills.

### Paper and drawing style

- **Paper:** 24px dots by default (1px, `color-mix(muted 32%, transparent)`). Plain is allowed. Mark, 2026-10-25: dots read better than the grid once the pen was in; 24px chosen from 12–32px (Explorations, "Dot spacing").
- **House style:** precise flat boxes with neutral outlines (rounded 10px), no shadows; groups drawn as loose hand-drawn marker loops (`feTurbulence` baseFrequency 0.012, scale 8–9, rx 28) in the group hue; labels outside boxes in **Kalam, lowercase**, written lowercase in the Mermaid source rather than by CSS, so literals keep their case (HTTP verbs, status codes, paths, identifiers, code, acronyms: "GET /login", "send logs (TLS)"; a composite state takes an alias, `state "running" as Running`); labels inside boxes in the UI sans (Segoe UI / Arial metrics). A composite state is a group like any other: loop and label, no title rule across it.
- **Chalkboard** stays as an alternative style for proposals and "how I'd approach this" posts.

### Pen

Mark, 2026-10-24, after [pele-art-diagrams](https://pele-art-diagrams.vercel.app/) (Pele lays a diagram out, then a program redraws it with a simulated pen) and three test rounds (`scratch/2026-10-24-hand-drawn-test/`): he liked hand-drawn boxes and hatched fills, and wanted handwriting kept out of the names.

- **Principles:** layout stays exact and only the drawing is by hand, so the spacing rules still hold; a light hand (fit for work, never rough); hatching is spent like colour, on what the diagram says.
- **Rules:** boxes and lines wander lightly and close where they start; group loops wander most and run 5–10px past their start; the focus's tint becomes hatching in its colour, *under* its text; names in boxes stay in the UI sans; labels between boxes, group and frame labels, and notes stay Kalam.
- **Style E (default):** only the focus is hatched. **Style D (an accepted option):** every plain box is hatched faintly in its outline colour, with the focus still strongest: `data-pen="all"` on a figure. `data-pen="off"` keeps a figure clean.
- **Where it runs:** in the reader's browser (`pen.js`). Without JavaScript a post shows the clean diagram; the pen redraws when the colour scheme or `data-theme` changes. Baking it at build time would fix the colours and break theming, and would need a browser in the static build.

### Icons

- Use real brand icons for known services (Simple Icons, CC0), generic icons for our own components (Lucide, ISC). Pinned: `@iconify-json/simple-icons@1.2.100`, `@iconify-json/lucide@1.2.147` (`@iconify-json/logos@1.2.17` was only for the comparison).
- **Icons are never coloured.** Every icon is **inverted**: dark mark on a light tile.
- **The tile always sits inside a box**, so the box can carry emphasis (Mark: a box is needed to highlight). Architecture: treatment **A2**. Sequence: icon tile **to the left of the name** inside the participant box (**S1**).
- Icons replace subtitles; keep a subtitle only when it adds something ("raw copy", "443 · TLS").
- Pele keeps the requested name in `data-icon` and draws a generic glyph; the build swaps in the real icon.

### Spacing and padding

- Text keeps **3px** clear of any line except its own straight line; a label must not touch a curve or loop, even its own.
- Text inside a group or frame keeps **4px** from the outline.
- Sequence frames grow **12px** each side and **8px** top/bottom, but the top only grows into free space (min 8px gap to the message above); whatever it can't grow, the frame tag moves down.
- Self-message labels sit to the **right** of their loop (10px gap).
- **Principle:** a group label belongs inside its group, top or bottom, whichever has room; outside only as a last resort, because a label far outside reads as detached (Mark, 2026-10-24, on the cache diagram's "system of record").
- Group labels go in the **widest stretch of the top band no line crosses**; else in a band added along the bottom (the group grows by the band, and widens evenly by up to 80px when the label is longer than the group and no line crosses the bottom); else just outside the group's top-left corner.
- Frame labels and notes never sit on a lifeline. A margin note sits on a background-coloured chip (no outline), so lifelines pass behind it; else labels get Pele's own chip, widened for Kalam (`frameLabels`).
- A node label with an explicit `<br/>` in the source is a title and subtitle (bold, then small muted); a name Pele wraps to fit is one name in one style. The SVG can't tell them apart, so `fixAll(svg, source)` / `fixDiagram(svg, { source })` marks subtitled nodes from the Mermaid source (`pele-subtitled`), and the stylesheet styles only those.
- Text inside a shape is centred in it, both ways. Sequence frame tags are re-centred with a central baseline on a pill 5px taller (`centreTags`), since Pele centres them for its own font and Kalam sits low. Pele sometimes draws the label in a separate `pele-cluster-titles` overlay with a halo copy; both texts move together.
- A label on a line with a bend moves to the middle of that line's longest straight stretch; when the stretch is shorter than the label, it goes beside the stretch on the outside of the bend (`labelsOffBends`). Pele otherwise puts ER labels right where the bend ends.
- When the check still fails, change the Mermaid source (direction, fewer crossings, shorter labels).
- Icons sit **4px** inside a **20px** tile.
- The Diagrams page shows these rules as an anatomy, not a fix: the S1 sequence with each clearance measured by a numbered orange band (orange is the measurement layer there, not a diagram colour) and the rules listed beside it.

### Handwritten notes

Mark, 2026-10-24: both Sonnet and Opus independently added a handwritten bracket stating a chart's takeaway; Mark wants notes on every diagram type, to explain things or add to them.

- **Principles:** a note says what the diagram can't (the number the caption implies, why, a caveat, what travels on a line that can't be labelled); it sits beside what it explains, with a leader or bracket when it can't; notes are sparing.
- **Rules:** add them after `fixDiagram` with `addNotes(svg, [{ x, y, text, emphasis, path }])` (diagram coordinates; it styles them and grows the drawing), positioned from `locate(svg, id)` so they follow the layout; Kalam, lowercase, muted, pink only when pointing at the emphasis; a few words, at most two lines; the overlap check covers them; architecture lines take a note for what travels on them, since Mermaid can't label them.
- Kalam's 5 reads as an S, so text holding a code like `5xx` is set in the UI sans (`literalCodes` marks it `pele-literal`).
- Chart bars are neutral outlines; `barIds` numbers them `bar-1`, `bar-2`, … and their value labels `value-1`, `value-2`, … so a bar and its value can be emphasised by `data-id`.

### Article layout

Mark, 2026-10-26, reworking the Opus rewrite of the OPW walkthrough; the rules are in the skill's `references/html-presentation.md` (Desktop layout, File pills and the viewer) and `references/implementation-walkthrough.md`, and on the Article layout page.

- **Principles:** text fills the column; components are set in and sized to their content; components and diagrams are centred; use the width for content, not margins.
- **Rules:** one content column of min(1040px, 100vw − 352px) from 1100px; code, tables, callouts and disclosures one tab (48px) in; figures as wide as their diagram, the terms figure inset-wide; a diagram under half the column takes its text beside it; a sticky contents list from 1200px; repo cards three across as vertical cards, no side strips; an index of every changed file grouped by need; file pills name lines and open a viewer. - Writing style is not a design page: it lives in the skill's `references/explanation-style.md`.

### Layout

- Fits the 720px article column (692px inside the figure's padding); redraw top-to-bottom when wider.
- Render at natural size. A gantt, timeline, xychart or quadrant chart wider than 692px is rendered again with `--width 692`, so it lays out to fit instead of being shrunk. Sequence, flowchart, state and architecture diagrams are never narrowed this way: Pele wraps their labels and squeezes their spacing (the Sonnet review's sequence diagram, 2026-10-24).
- Source patterns that keep labels clear:
  - **Timelines** go vertical: `timeline TD`. Horizontal timelines run past the column after four or five periods.
  - **Git graphs** go vertical with unrotated commit labels: `gitGraph TB:` plus `config: gitGraph: rotateCommitLabel: false` in front matter. Horizontal, branch curves run through the labels of the commits they leave or join.
  - **Two-way state transitions** (A → B and B → A) go in a left-to-right group (`direction LR` inside the composite), so both labels ride straight stretches. Stacked vertically, Pele draws the pair as S-curves whose straight middle is shorter than a label.
  - **Don't label a line with what its target already says** ("raw" into a box subtitled "raw copy").
  - Pele reads `nodeSpacing` and `rankSpacing` from Mermaid config, but state diagrams take them only in the `%%{init: …}%%` form, and neither lengthens a pair's S-curve. At most about 9 boxes. Emphasis on 1–2 things, density about 4/10, delete before adding (borrowed from diagram-design).
