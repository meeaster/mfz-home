## Why Mark wants a redesign

The instructions had accumulated through revisions by different models. Mark wants to reconsider whether their structure and individual requirements produce the intended behavior, rather than merely polish existing wording. The primary purpose is a useful session where he can think and direct work without loading every investigated source file into its context.

The workspace supports two related needs. It preserves working context across compaction, and it lets later agents use earlier work. Research should inform implementation without having to repeat the investigation. Operational discoveries should help another agent avoid the same failed commands or environment mistakes.

Chief mode originally allowed a capable model such as Astra to discuss high-level ideas while a cheaper orchestrator such as Sol coordinated other agents. Mark currently prefers direct interaction with the orchestrator so he can observe and refine its behavior. He wants Chief mode available for later use, without making the extra layer the organizing assumption of the whole skill.

The cost goal concerns total useful work across the agent tree. A cheaper individual call is not necessarily cheaper overall if it causes repeated handoffs or duplicated reading. Keep enough understanding in the human-facing session for good judgment while delegating source-heavy investigation and execution.

## Human-facing roles and delegation

### Direct orchestration

The current session is the orchestrator and Mark's thinking partner. It reasons about options, challenges consequential assumptions, develops recommendations, and communicates with him. It delegates source investigation to evidence-gathering agents and execution to the appropriate agents.

Direct interaction gives Mark visibility and steering ability. It does not require approval of every evidence-gathering dispatch. When the request is reasonably understood, bounded evidence gathering is proactive.

### Chief mode

The Chief keeps high-level brainstorming, advice, design discussion, and human decisions in its context. It delegates evidence gathering and execution through an orchestrator. It can brainstorm directly from available context without launching a cycle merely to have a conversation.

The Chief communicates needs much as Mark would: what is being considered, why, which constraints matter, what information would help, and what action is authorized. The orchestrator chooses the investigation methods, agents, task decomposition, and dependency ordering. A normal Chief brief is not a prescribed dispatch plan.

An example request is to compare two approaches on migration cost and future integration constraints while explicitly withholding implementation authority. The orchestrator should determine how to obtain that evidence and return a supported answer.

The Chief receives a concise result with workspace pointers. It may read the orchestrator's evidence directly when a claim or decision warrants closer inspection. The return message is an entry point, not its only permitted view. Access does not require reading the entire workspace.

### Mode selection and independent scopes

Only Mark selects or changes modes. Agents neither change mode nor recommend switching. An explicit human request can change mode, including after compaction. This supersedes the earlier recommendation to suggest mode changes when useful.

Chief mode can coordinate several independent orchestrators, such as three unrelated GitHub issue investigations. Reuse an orchestrator for a coherent workstream. Different workstreams may run concurrently, but requests to one orchestrator remain sequential. The parent coordinates overlapping write scopes and integration. Worktrees are not automatically authorized.

### Direct-reading exception

Both human-facing roles retain substantive reasoning but delegate implementation-source investigation, even for a single code file. Small overhead does not justify eroding this boundary.

They may directly read identified instruction, design, and prose artifacts whose exact wording or structure is the subject of evaluation or revision. Examples include a skill being rewritten, an architectural document under discussion, or an identified Confluence page being revised. A summary would lose the very content under judgment.

If the artifact is unknown, delegate discovery first. If Mark already names the exact artifact, a preliminary discovery dispatch is unnecessary. This exception does not cover implementation source code merely because one file is being discussed. Supporting research still follows normal delegation.

## Agent vocabulary, authority, and verification

Use agents or subagents as the umbrella term. Do not call every agent a specialist.

| Function | Examples |
| --- | --- |
| Evidence gathering | `explore`, `research`, `inspect` |
| Implementation and operations | `worker`, `operator` |
| Design advice | `architect` |
| Review | `reviewer`, `pr-reviewer` |
| Authoring | `agent-author`, `artifact-author` |
| Session analysis | `session-analyst` |
| Workspace transcription | `scribe` |

Categories describe responsibility, not authority or a permanent model price tier. Select models through actual agent configuration and explicit user choices.

An implementation request authorizes a proportionate workflow to deliver the outcome. Investigation, necessary design assistance, implementation, verification, review, and remediation can fall within it. They are not mandatory stages for every task. Existing sufficient evidence can eliminate a redundant investigation. A one-line profile enablement may need only a settled operation and activation check.

During exploratory discussion, expensive consultations or authoring work should be recommended before dispatch. During authorized delivery, use them when the task materially needs that expertise. Ask about consequential choices outside the request or unusually expensive expansions. Do not turn words such as "implement" or "update" into rigid routing triggers.

Mark can authorize a whole sequence, such as consulting the architect, selecting a design, implementing, reviewing, and fixing findings. This also authorizes ordinary verification between those stages even if he does not name `inspect`. Avoid repeated permission requests while the basis of authority remains stable.

Operational decisions belong to the orchestrator. Changes to goals, scope, architecture commitments, or meaningful tradeoffs return to the human or Chief unless decision authority was delegated. Return a recommendation and evidence, not merely an unanswered question.

Verification is proactive and proportionate. Trust concrete worker verification for small, straightforward work. Use an independent factual check when changes span components, touch external systems, have uncertain results, or lack convincing verification. Recommend or perform authorized review when design quality, maintainability, or subtle correctness warrants it. Size alone is insufficient: a one-line deployment change may need independent checking.

Coordinator acceptance checks whether the result answers the assignment, respects authority, supplies adequate evidence, and exposes uncertainty. It does not repeat the investigation by default. Contradictions or missing support lead to focused follow-up. Producer completion, coordinator acceptance, independent verification or review, and human acceptance remain distinct claims.

## Workspace structure and ownership

The same structure applies to an orchestrator at the root or inside a delegated workstream:

```text
<effort>/
  context.md
  coordination.md
  index.md
  design.md
  evidence/
  learnings/
  synthesis/
  workstreams/
    <delegated-scope>/
      context.md
      coordination.md
      index.md
      design.md
      evidence/
      learnings/
      synthesis/
```

Create only needed files and directories. Establish a workspace when substantive investigation, delegated execution, or decisions worth preserving begin. A short preliminary conversation need not create one.

In direct mode, evidence lives directly in the effort workspace. There is no universal `assignments/` wrapper. Nested workspaces separate independently coordinated scopes, which was the original reason for introducing orchestrator subagents. In Chief mode, root files hold relevant human-facing and cross-workstream state, while each orchestrator owns its nested workspace.

| Location | Purpose |
| --- | --- |
| `context.md` | Purpose, background, scope, constraints, accepted decisions, and consequential rationale |
| `coordination.md` | Active assignments, session handles, progress, blockers, next steps, and continuation state |
| `index.md` | Material locations, relevance, and qualifications or supersession |
| `design.md` | Optional accepted technical design shared across work units |
| `evidence/` | Task-shaped research, results, verification evidence, and other producer deliverables |
| `learnings/` | Optional operational lessons from producer assignments |
| `synthesis/` | Documents explicitly requested to preserve a discussion in depth |

`design.md` retains its original role: accepted boundaries, responsibilities, flows, interfaces, invariants, and tradeoffs. It is neither a task list nor blanket implementation authority. Clearly label remaining open details. Competing proposals remain separate until a direction is accepted.

Maintain working records when meaning or state materially changes. Avoid duplicate descriptions across files. Dispatch a short explanation of how the assignment fits the effort when sufficient; point to `context.md` when broader constraints or history matter. Do not require every agent to read the whole workspace or repeat file contents in the prompt.

## Evidence and operational learnings

Task evidence has the shape its task needs. A research report already contains the information the agent was asked to discover. It does not need a second copy labeled findings.

Operational learnings are incidental discoveries that improve another agent's ability to work. For example, after several failed CLI attempts, preserve the command that worked and the condition that explained the failure. They can arise during inspection, implementation, operations, review, or research, but no role must invent them.

- Each producer assignment has its own optional learnings file. Concurrent agents never share a write target.
- Use concise bullets. Include the problem, relevant failed approach, working method, and conditions needed to apply the advice correctly.
- A producer continuing the same assignment can update its file. A new assignment gets a separate file, even if the agent session is reused.
- Do not duplicate learnings already supplied to the producer. Record new lessons or material corrections.
- Corrections identify the earlier note and the relevant conditions. Producers do not rewrite another producer's file.
- The orchestrator reads new learnings, indexes their relevance, marks supersession or qualifications, and routes selected files to later agents.
- After compaction, use the index to find relevant learnings rather than loading the entire collection.
- The Chief normally receives substantive results, not all operational learnings. Read those when they affect a decision, explain a blocker, or are requested.

This replaces the proposed alternatives of one global findings file, splitting every observation into its own file, or having the orchestrator routinely extract findings from verbose result records. Producer ownership reduces duplicate reading and preserves the conditions the producer just observed.

Substantial assignments receive owned output paths. Trivial results can return directly or enter existing coordination state. Bounded continuity checks may return without files. No empty evidence or learnings file is required merely to satisfy a universal note policy.

Reuse within an effort is automatic. Promotion into permanent skills or maintained guidance requires authorization. A local workaround must not silently become universal policy.

## Requested synthesis

Synthesis is never automatic. Agents may recommend it when a discussion has produced reasoning worth preserving beyond working-state notes, but task completion or conversation length alone is not a reason to keep prompting for it.

When requested, preserve goals, decisions and reasons, alternatives, rejected approaches, corrections, tradeoffs, and unresolved questions. Distill repetition without strengthening claims or compressing away qualifications. A request to synthesize is not necessarily a request for a short summary.

The human-facing coordinator owns conclusions and reasoning. Scribe may record established content in a requested synthesis document but does not independently resolve contradictions or invent recommendations. An authorized authoring agent can own a suitable artifact assignment. Delegated orchestrators likewise do not create synthesis files without authorization.

Automatic context and coordination maintenance can preserve material rationale needed to continue. That is distinct from creating an integrated account of the conversation. Ordinary task returns can explain results without becoming synthesis documents.

## Scribe lifecycle

Keep Scribe for now. It began partly as an output-cost optimization; changed model economics may justify making it optional later, but that is not this decision.

Only the human-facing session has a Scribe. In direct mode that is the orchestrator; in Chief mode it is the Chief. Delegated orchestrators maintain their own coordination records. Producers write their own evidence and learnings.

The human-facing session owns the meaning of its records. Scribe transcribes that meaning and maintains files. There is no required Scribe round trip before every dispatch.

A new Scribe receives the parent session ID and reads without a marker. A reused Scribe is explicitly told to continue from its last successfully read marker. The Scribe owns that marker and follows chunking. An empty delta must not erase the last usable marker. Reuse must not silently become a full reread on every dispatch.

After parent compaction, the old Scribe completes a continuity check and any outstanding writes, then a new Scribe takes over. Preserve the old session handle. Only one Scribe has write ownership at a time. A fresh `inspect` agent is the fallback if the old Scribe is unavailable or cannot complete recovery.

## Automatic post-compaction continuity

Mark rejected recovery only when the model detects a gap. A model may not know what was omitted. The accepted default is a background continuity check after each recognized completed compaction.

Compare the preceding active window with the current checkpoint and workspace. Return useful additions or corrections concerning user requirements, decision status, material rationale, unfinished commitments, active work, and unresolved questions. Include useful source locators. No material additions is a valid result. Do not return a broad historical recap merely because history was read.

Continue conversation and independent investigation while the check runs. Incorporate its result before new consequential dispatches, implementation decisions, or final completion claims. Already-authorized work in flight can continue. Material corrections enter ordinary working records without requiring a synthesis document.

Initially this is an instruction-level requirement. It is not a guaranteed event callback. Reliable event-driven triggering would be separate tooling work. Never initiate compaction without the human's explicit request.

The earlier preference for explicit-only historical recovery was superseded for this bounded post-compaction check. General historical exploration still needs a relevant assignment. Scribe's named-session pulls are authorized as part of its record-maintenance assignment.

## `session_context` extension

Add boolean `previousCompaction`, default `false`.

| Value | Selected context |
| --- | --- |
| `false` or omitted | Existing current active window |
| `true` | Active window immediately before the latest completed compaction |

Use the existing `sinceMarker` and chunking mechanism inside the selected window. Do not introduce a general historical-window selector for this request. If the marker is absent, report that fact and return the full selected window. Never silently substitute the current window for the previous one. If no previous window exists, return an explicit no-previous-window result.

The previous window includes the preceding completed checkpoint, when present, and subsequent messages before the latest completed compaction. Include a checkpoint's retained recent conversation alongside its summary for useful recovery. Preserve the documented filtering of tool output and other omissions; this is not a lossless source-file substitute.

The old Scribe can use its existing marker with `previousCompaction: true` to read the unread tail. It then compares against current context, finishes records, and returns corrections before rotation. A fresh recovery agent can read the complete previous window.

Before this change, the tool called `session.context`, which exposed only the latest completed compaction and later messages. A stale marker fell back to the current window. Thus an old Scribe could retain previously read information but could not recover an unread pre-compaction tail through the tool. Parent compaction does not change the parent session ID, so an existing child remains resumable, subject to its own context limits.

## Writing policy and validation

All runtime text is for the LLM. Human readability helps Mark inspect what it asks the model to do. Use focused sections and choose the form by purpose: short prose for context and rationale, bullets for independently applicable rules, tables for comparisons or repeated relationships, and numbered lists for genuine ordering or dependencies. Do not impose one format throughout or create mandatory stages merely for visual consistency.

Local writing preferences belong in the owned Skill Authoring skill, not its vendored Writing for Agents dependency. Preserve concrete meaning when shortening. Treat prompting-mechanism claims as hypotheses unless supported by relevant evidence.

Validate the tool's window boundaries, marker behavior, chunking, missing-window behavior, and rendered plugin loading. Check instruction links, role ownership, invocation, consumers, record alignment, and selected behavioral scenarios. Static consistency and activation do not establish improved model behavior or lower costs.

Earlier Context Transfer experiments compared four paired routine delegation tasks with Sol medium coordinators and Luna high workers. They supported retiring generic mandatory briefing guidance, with small treatment benefits and substantial limits. They did not test orchestration topology, universal producer notes, long-context recovery, or specialist artifact preservation. See [the retained experiment account](../context-transfer/delegation-experiments.md). Do not use those results as proof of this redesign's effectiveness.

## Superseded assumptions and deferred work

- No mandatory standing gateway is imposed on direct mode; Chief can own several independent workstreams.
- No universal `assignments/` layer or mandatory note for every trivial producer return.
- No automatic synthesis file, whether singular or inside `synthesis/`.
- No mode-switch recommendation by the model.
- No rule that all expensive agent calls require separate approval after a delivery workflow is already authorized.
- No symptom-only recovery policy for post-compaction continuity.
- No whole-history reread on every Scribe reuse.
- No automatic permanent promotion of operational learnings.

Making Scribe optional, guaranteeing compaction callbacks, broad comparative cost experiments, and changing configured model selections are deferred. The agreed rewrite should preserve meaningful specialist artifact detail and explicit correction overlays, environment permissions, publication boundaries, and applicable verification requirements while reconciling the old contracts with this design.
