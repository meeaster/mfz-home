# Vision

## Shared ownership and contexts

The human accepted moving the complete workflow from `/orchestrate` into one shared `skills/active/orchestrator-mode/SKILL.md`, without progressive reference splitting. The skill ID is `orchestrator-mode`, displayed as `Orchestrator Mode`, to describe the operating mode. The command is a thin explicit human-facing loader; the frontmatter-only `orchestrator` agent is a parent-facing consumer whose caller must explicitly request the skill load and carry context and delegated authority. Neither automatic skill discovery nor task complexity selects this workflow. One explicit human orchestrator selection can cover several bounded children in a named batch.

The intent below originated with the command and remains the behavioral contract for the shared skill. Command argument mechanics stay in the command's record. Root or primary ownership below means the local coordinator owns gatherers and specialists, not that the assigning parent must mediate every evidence request. Human dialogue and consequential choices remain with the main session; a parent-facing coordinator returns these to its assigning parent. The child may make prospectively delegated design selections and execute the full explicitly authorized sequence through a PR while the basis remains valid. A PR request includes necessary in-scope commit and push, not merge. Review plus remediation covers corrections and verification, not automatic independent rereviews.

At the unchanged depth limit, specialists beneath orchestrator return evidence needs to it rather than delegating. This does not change ordinary main-session worker delegation. Skills and conversation are not inherited. The parent transfers decision-relevant context and requires explicit permitted skill loads. Orchestrator never recursively dispatches itself and routes consequential questions through its parent. Its model is unset to preserve documented parent-session inheritance.

## Task evidence intent

The human requires task-local file-backed handoffs for every evidence-producing dispatch in both invocation contexts. Small findings may grow into later investigations, so file creation does not depend on predicting reuse or task size. Use `/tmp/opencode/orchestrator-evidence/<effort>/`, explicitly approved instead of workspace scratch after examining V2 path matching. Sessions remain outside this root and the root must be external to each writer's Location and project. The human accepted edit capability for any file beneath the root and later authorized a same-name Explore override preserving its complete upstream prompt except a requested-only evidence-writing guideline. Small requested-write allowances also reconcile owned evidence-agent role prompts. Producer ownership, assignment directories, and file layout remain behavioral constraints. Permission and skill loading alone grant no assignment. Genuine instruction conflicts retain the coordinator-owned attributed fallback rather than forced writes or silent role substitution.

The prompt owns the current assignment, required constraints, authority, and required reading. Optional `context.md` explains background intent or rationale, never additional work. The coordinator owns workspace structure and a concise selective `index.md`; producers own coherent notes through the explicitly loaded `orchestrator-task-evidence` skill. That lightweight skill owns note production, reuse, updates, attribution, freshness, execution lessons, and completed-note handoffs. Orchestrator Mode owns explicit file assignments and skill-load briefs, directory ownership, selective pointers, missing-evidence coordination, and nesting without recursive orchestrators or a changed depth limit. ## Problem

Primary models are valuable for analysis, decomposition, and acceptance, but using the coordinator session for implementation spends its context on work a bounded worker can execute. Ad hoc delegation also produces weak briefs, overlapping agents, unauthorized mutation, and expensive review loops.

Observed session evidence showed a communication-first HTML worker could produce and correct the artifact, while the coordinator duplicated artifact skill and reference loading and retained large source and screenshot payloads. The stable `artifact-author` boundary is the intended human consumer: it turns working context into a durable artifact that another person can understand, review, decide from, or use. That transfer requires deliberate selection, explanation, organization, context, provenance, and presentation beyond agent-internal evidence notes, raw transcripts, implementation handoffs, or ordinary chat responses. The role keeps destination references, full source, screenshots, and iteration history with one child.

Concrete uses include creating a Confluence design document after research and accepted option development, publishing a curated evidence synthesis, creating an HTML explanation or discussion aid, and recording decisions, options, rationale, findings, or recommendations for people outside the producing session. Raw orchestration evidence notes remain producer-owned internal handoffs; selecting and publishing a human-readable synthesis from them is artifact-author work. Confluence through `confluence-writer` and self-contained HTML through `visual-explainer` are the first grounded destination workflows, not the semantic limit of the role. Profile selection supplies additional available craft or brand skills.

## Intended behavior

The user owns the orchestration process. All workflow rules below are defaults subject to an explicit user request to skip, replace, or waive them, including delegation, planning, review, verification, and repeated approvals. The coordinator carries overrides into child briefs and continues without re-asking. Overrides remain scoped to the requested outcome and do not override higher-priority instructions or tool permissions.

`/orchestrate` keeps the current session and its selected model as an opinionated collaboration and design partner. It maintains the effort's shared working model, challenges assumptions, weighs options, makes recommendations, routes each authorized bounded unit to the specialist that owns it, and synthesizes returned evidence. The coordinator may use an owning workflow to record an explicitly requested planning or design artifact, but it does not implement or change operational state.

The invocation arguments are the user's raw current prompt, placed once at the end of the command under a `User prompt` boundary so they remain recent and distinct from the orchestration instructions. The input may be a settled task, question, correction, partial thought, brainstorming, spoken-style exploration, or context that relies on the prior conversation. The coordinator interprets it naturally in that conversational context rather than prematurely treating it as a settled task, implementation request, authority grant, or predefined workflow phase. Normal OpenCode argument substitution preserves the text for ordinary interpretation without wrapping it as code or data.

The command routes static local file evidence to `explore`, authoritative external documentation, releases, registries, and upstream metadata to `research`, and current or command-derived repository, runtime, cloud, deployment, or work-system facts to `inspect`. Read-only evidence gathering that requires command execution belongs to `inspect`, while `explore` and `research` remain non-shell lanes. Materially different local-static, external-authoritative, and current or live evidence becomes separate bounded source-gathering units. `triage` remains a goal-oriented diagnostic specialist for one reported symptom rather than a generic shell lane. The command runs independent read-only work in parallel and keeps broad evidence gathering outside the primary session; this autonomy grants no authority for architecture consultation, mutation, or review. The primary owns architecture-specific evidence gatherers and, before an `architect` engagement, explains why specialist synthesis is useful at that point, summarizes the evidence and pending decision, and confirms explicit human authority without hardcoding models, providers, prices, or cost tiers. One bounded engagement may cover consultation, material evidence follow-up, and reconsideration within the same decision and system boundary. The architect develops credible options and recommends one; the primary surfaces the substantive packet, preserves user dialogue, challenges the result, and retains acceptance and authority decisions. Architect output cannot accept itself or broaden authority. Implementation of a bounded result may continue only when the user's concrete sequence authorized it and no consequential unresolved choice or material change intervenes. Explicitly authorized behavioral instruction analysis or editing goes through `agent-author`; transformation of accepted or supplied working context into a durable artifact for another person goes through `artifact-author`; explicitly authorized throwaway logic, state-model, and UI artifacts go through `prototype`; settled procedural and operational mutations go through `operator`; application and OpenSpec implementation, substantive code changes, focused remediation, difficult implementation investigation, and novel troubleshooting go through `worker`; focused independent verification goes through `reviewer`; holistic pull-request due diligence goes through `pr-reviewer`. Both review lanes require an explicit review request, which may be supplied prospectively as a named step.

Agent Author owns interpretation, evaluation, design, or revision of AI-consumed instructions for their effect on agent behavior. Explicitly requested or authorized analysis returns findings or proposals without edits; adaptation requires editing authority. Artifact type alone does not select the author. Settled generation, installation, copying, or upstream refresh as supplied belongs to operator, which verifies the procedure and result and surfaces customizations or unresolved decisions. A refresh neither mandates author review nor authorizes gated analysis. Source-only what-changed comparison remains explore, command-derived evidence remains inspect, and generator errors retain the diagnostic gate. Select the owning role before continuity; retained author evidence does not keep a now-procedural refresh in the author lane.

Bounded consultation authority covers `architect` and `ui-ux-designer`. An explicit request or approval authorizes evidence return, corrections, and follow-ups within the same decision, scope, access, and system boundary without repeated approval. Materially new consultation, expanded scope or access, and an independent second opinion need approval. Consequential user choices remain in the primary session, and consultation accepts no design and grants no mutation or publication authority. Session availability affects continuity, not authority: a replacement session may continue the same approved engagement. The opening waiver remains authoritative over command-owned defaults.

The existing `ui-ux-designer` is an optional consultant for implementation-ready interface direction or critique when specialist design judgment is useful. An explicit UI-design request already authorizes appropriate consultation; otherwise the coordinator explains the need and asks. The caller requires `ui-ux-design` and a read-only handoff with task-relevant layout, interaction and component states, accessibility, constraints, and verification. The primary surfaces the direction for user acceptance or revision before proposing implementation or requesting its separate authority. System boundaries remain with architect, runnable artifacts with prototype, and implementation with its separately authorized owner. Settled UI edits do not require design consultation.

Production context informs architecture without selecting a transition strategy by itself. For a consequential production transition, the coordinator and any approved architect test whether a compatibility-first or staged approach and a careful direct cutover are both credible. When they are, both remain responsible options and the recommendation follows concrete facts about affected clients, persistent data or schema changes, tolerated interruption, rollback and recovery, observability, reversibility, dependency coordination, and temporary-machinery cleanup. Hard constraints such as unacceptable irreversible loss or uncoordinated consumers can make direct cutover non-viable; absent a concrete need, production does not justify compatibility layers, fallbacks, dual paths, or staged rollout. Execution safety depends on the operation's evidence, impact, and recoverability rather than a production-only gate.

Upstream evidence routing distinguishes publication facts from repository internals rather than treating GitHub as one evidence class. Published documentation, release pages or APIs, package registries, and upstream metadata remain research work even when hosted on GitHub. Questions requiring source-tree search, cross-file relationships, implementation details, or history use root-owned explore against a local clone. The coordinator first checks the canonical clone index and capability files, then reuses a suitable clone or directly performs bounded disposable clone, fetch, and exact-ref checkout preparation under `/tmp/opencode` before dispatching root-owned explore. This narrow coordinator exception avoids a ceremonial preparation child; a source-inspection request supplies only that temporary evidence-infrastructure authority. Private access, durable placement or publication, destructive broad cleanup, credentials, canonical-reference edits, and upstream Git actions remain separately authorized. One focused raw-file retrieval may remain with research when cloning is disproportionate and no cross-file or history judgment is needed.

External-system mutation uses proportional preflight rather than mandatory review. Small, narrow, understood, readily reversible operations go directly to the authorized operator. The coordinator gathers additional evidence only when material uncertainty, impact, live-system dependencies, selectors, access, blast radius, or recoverability warrants it, and gives the operator decision-relevant evidence without requiring duplicate broad collection. Before acting, the operator must understand the exact target and effect, applicable operation semantics, credible affected resources and dependencies, realistic impact, and practical recovery.

Relevant pre-change state is inherent read-only preflight whenever the system exposes it safely and meaningfully. The operator captures only what identifies and verifies the target and can restore mutable configuration, excluding secrets, unrelated sensitive content, volatile fields, and non-reapplicable fields. A narrowly scoped restoration file is optional; session or tool evidence is sufficient when practical. If meaningful state cannot be captured, the limitation and recovery consequence remain visible.

State capture is distinct from backup. An existing on-demand backup, snapshot, or export that could materially improve recovery requires user authority unless the accepted sequence already includes it, with known material cost, duration, retention, and system effects disclosed. The workflow does not build backup infrastructure, alter independently managed automated backups, treat their existence as proof of restorability, or block a responsible operation solely because no backup mechanism exists. Immediately before mutation, the operator revalidates consequential assumptions and uses the narrowest correct action; afterward it reads resulting state and verifies the outcome and important invariants. Stop conditions cover material differences in target, state, impact, recovery, procedure, or authority. Reporting preserves residual effects that restoration cannot undo.

Mutation authority is outcome-scoped. A concrete request may prospectively authorize multiple named gated steps and their necessary inherent operations, so the coordinator does not seek redundant approval as each step arrives. That authority persists only while outcome, target, scope, system boundary, access, consequential resource commitment, risk, reversibility, assumptions, validation, and required authority remain materially consistent. A material change, unresolved consequential decision, failed gate, different procedure, independent new outcome, broader work, missing authority, or user-relevant blocker pauses downstream work and is surfaced with the smallest needed decision. Unknown ordinary implementation details do not invalidate an otherwise conforming sequence. Vague future steps grant no authority. A commit does not imply a push, a push does not imply a pull request or merge, a draft does not imply publication, and one system update does not imply another. Artifact-author may complete an explicitly approved publication step only when it is inherent to the owning editorial lifecycle; mechanical Git operations, deployment, and publication outside that lifecycle remain operator work. Disposable upstream clone preparation implied by a material source-inspection request grants no broader mutation. Operations may be combined only when they are inherent to one explicitly requested transaction or named in one concrete sequence; otherwise the coordinator keeps them as separate bounded operator units.

The parent command has one narrow OpenSpec sequence exception. An explicit proposal-then-Apply or proposal-then-implementation request authorizes two separate workflow units: `openspec-propose` remains planning-only and stops after producing and presenting or checking its artifacts, then the coordinator checks them and may start a fresh Apply or implementation worker under the original authority. A material proposal change or consequential unresolved choice pauses. Proposal-only requests stop, and direct `openspec-propose` invocation retains its own new-request boundary.

Mutation and prototype creation begin with a proportional preparation decision. Once mutation is explicitly authorized and settled, the coordinator dispatches its owner directly. The mutation agent owns ordinary immediate preflight, including instructions, status and diff, dirty-state preservation, relevant Git topology, validation, artifact safety, and final-state checks. Separate `inspect` remains for a requested read-only outcome, absent mutation authority, or readiness that depends on a distinct live system, access boundary, or human decision. Substantial mechanically separable preparation uses an explicitly authorized operator when it changes the brief or state or protects build context. The coordinator verifies the prepared state and normally starts a fresh prototype, artifact-author, or implementation worker under the shared transfer contract, carrying the accepted design, question, or communication-artifact contract, user priorities and tradeoffs, material uncertainty and evidence, and verified assumptions without mechanical setup history. An artifact-author handoff also preserves audience, destination, owning workflow, source fidelity, and publication state or authority. A sequence naming preparation and build may continue without another turn only when the handoff preserves those assumptions. Preparation and the artifact build are serialized when they share mutable state, and their work does not duplicate ordinary mutation preflight.

Production, shared-environment, destructive, cross-resource, broad-selector, IAM/access, networking/routing, monitoring-suppression, poorly reversible, or unclear-blast-radius external operations often justify more evidence than ordinary operator preflight. The coordinator adds only evidence tied to credible impact or recovery paths and pauses only when a material uncertainty, changed assumption, or authority boundary remains. This is proportional judgment, not a fixed multi-agent process or automatic approval cycle.

Mutation decomposition precedes scheduling. Each unit has one primary accepted outcome, one coherent ownership boundary, and compatible acceptance and validation, grounded in its owned files and mutable state, domain, external or runtime state, dependencies, and integration requirements. The primary outcome and complexity select artifact-author, operator, or worker; touching a file does not. Semantic cohesion, not file, directory, repository, or change count, determines unit size. If discovery reveals multiple independent outcomes or keeps expanding without narrowing the accepted mutation, the agent stops through the blocker protocol rather than carrying broader work indefinitely.

Scheduling is a separate decision. Mutation agents run sequentially by default, and unknown overlap means serialization. Sequential fresh agents consume the verified state and compact handoff from the previous unit. Parallel mutation is an exception for demonstrably independent responsibility and mutable state with material concurrency value. Different directories do not establish independence: the checkout and Git index, lockfiles, dependency and installation state, generated output, test caches, active runtimes, schemas, and external systems remain shared unless explicitly isolated. Separately authorized isolated worktrees or environments may support parallel mutation, but shared-state integration and final validation are deferred. If combining isolated results requires mutation or a distinct shared validation outcome, an operator owns procedural integration and a worker owns substantive software integration; the coordinator never integrates by mutation. No integration agent is introduced when there is nothing to combine or no distinct shared validation outcome.

Preparation preserves unrecognized dirty state and resolves ambiguous synchronization intent before mutation. Routine state management and handling decisions do not justify diagnostic delegation even when they block continuation. Git, Jira, and environment changes remain independently authorized unless the user explicitly requests one transaction. A preparation handoff makes the assumed implementation state observable without carrying mechanical setup history into the implementation session.

Use the smallest adequate role for the needed cognitive outcome. Direct facts may answer a causal question without diagnostic judgment; neither "why," domain labels, apparent complexity, nor a more capable model justifies triage. Triage requires a concrete unexpected symptom that remains unexplained and a downstream decision that needs genuine diagnostic judgment. Apply this boundary to initial requests and mutation stops alike, without making inspection a mandatory preliminary step when that need is already clear.

One explicitly authorized coordinated operation may span known repositories under one sequential operator. Each repository retains its own instructions, validation, Git history, commit boundary, remote, and result. Cross-repository commit and push are not atomic. For authorized Git publication, the operator validates every repository before publication when practical, creates separate Conventional Commits when commits are authorized, and reports commit and push state per repository. Partial publication remains in place if a later repository fails; the coordinator reports exact state and the smallest recovery action instead of attempting destructive rollback. Repositories split across operators only when they are genuinely independent and parallel value outweighs coordination or sequential-safety concerns.

Operator and worker stops become coordinator-owned classification points. Operator and worker remain promptless; Triage owns only a small role and requested-evidence allowance. The coordinator puts qualitative troubleshooting, stop, and blocker-packet contracts into mutation briefs, and the read-only diagnosis boundary into blocker-triage briefs. Operator correction stays bounded to narrowing evidence within the settled procedure; novel troubleshooting, difficult remediation, or a shift to software behavior stops the operator. The coordinator checks blocker packets and starts fresh `triage` for an unknown observed symptom without transferring raw failed-command history. A checked procedural cause may continue through a fresh operator; novel troubleshooting or difficult remediation under the unchanged accepted outcome and authority goes to a fresh worker. Worker compaction remains advisory pressure rather than a numeric cutoff, and a bounded implementation cause may continue through a fresh worker. These looping-agent preferences do not displace bounded continuation for a child that stopped cleanly on one decision while retained context remains useful.

Possible design conflict follows no direct worker-to-architect route. The coordinator treats worker and triage findings as evidence, gathers the smallest necessary root-owned architecture evidence, surfaces the combined evidence and pending decision to the human, and explains why another architect turn would help. A follow-up within the same still-authorized bounded engagement resumes the existing architect without redundant approval; proposed design changes return to the user before remediation. A materially new or invalidated decision, new system boundary, or unrequested independent opinion needs fresh authority. Requirement, scope, access, and authority changes return to the human; implementation and environment failures that fit the accepted design do not involve architect.

Authoring is also outcome-scoped. Creating or revising an AI-facing artifact does not authorize broader application changes, publication, source-control operations, or independent approval. Communication drafting or updating does not authorize publication. Mixed prompt, communication-artifact, and application work uses separate specialist units when practical, with the primary owning their accepted interface.

Prototype creation is a first-class mutation lane, distinct from architecture synthesis and production implementation. It requires explicit authority to create a runnable throwaway artifact in an appropriate mutable or disposable workspace, and it applies only when that artifact tests one bounded, unsettled logic, state-model, or UI design question. Discussion, option exploration, or a suggestion to prototype remains non-mutating. The `prototype` skill owns artifact procedure; the coordinator may load it to classify and brief work but does not build the artifact. The child reports the artifact locator, observations, assumptions, and uncertainty, while the coordinator interprets the evidence and owns the decision. Production implementation requires separate worker authority, and prototype authority does not include commit, push, pull request, publication, Jira updates, deployment, or productionization. Generic technical-feasibility spikes remain outside this lane.

Review routing depends on the evidence contract rather than authorship provenance. `reviewer` covers correctness, maintainability, and substantive behavior-preserving structural simplification when the parent owns or accepted the design and knows the implementation brief and validation history. Code review explicitly loads `thermo-nuclear-code-quality-review`; accepted design does not reduce review to conformance. Structural simplification alone does not require `pr-reviewer`, which reconstructs and challenges an unfamiliar or unobserved pull request's intent, rationale, implementation, validation, and holistic merge case through `pr-review`. Major structural findings require a concrete problem and evidence, a plausible simpler alternative, actual benefit and material tradeoffs, and demonstrated effects distinguished from expected benefits or uncertainty. Both reviewers propose only; design or scope changes return to the user before remediation.

The primary owns broad PR evidence gathering. It reuses existing evidence and retained children, selects only materially needed `inspect`, `explore`, or `research` units, and supplies compact packets with session IDs, confidence, gaps, constraints, charter, authority, and stop conditions. Detailed traces remain in gatherer sessions. The reviewer uses its own tools only for focused checks or conflict adjudication.

When the reviewer returns complete single or batched missing-evidence requests, the primary checks materiality, duplication, scope, read authority, overlap, and existing answers; reuses relevant evidence and applies source-gatherer continuity rules; runs independent units concurrently and dependent units serially; checks every packet; and normally resumes the same reviewer once with checked packets and the material delta. Packet conclusions remain evidence to retest. Source/current/external gaps remain distinct from architecture consultation, user decisions, mutation, expanded access, and publication authority. The parent retains merge and design decisions and does not commission an architect routinely before PR review.

Information transfer is complete but proportional in both directions under `context-transfer`. Carry decision-relevant meaning not supplied by the destination, including intent, priorities, accepted constraints, uncertainty, scope, authority, verification, and stop conditions. Include exact critical evidence where details matter and accessible supporting locators; an inaccessible session ID cannot substitute for evidence. Omit transcript replay and unrelated context. Recipients load permitted relevant skills; the coordinator transfers operative guidance when a skill is unavailable or disproportionate for a small note. Compact source memory retains the session ID, decision context, verified evidence and freshness, open work, warnings, and routing guidance. Carry the latest relevant memory in the prompt or required shared-note headings, without accumulating chains or duplicating full notes. Memory remains evidence and cannot accept its own claims or change authority. Owning specialists retain full source, media, craft references, iteration history, and detailed traces, then return a compact acceptance packet. The coordinator evaluates that packet first and loads full payloads only for a material conflict or uncertainty, failed or inconclusive validation, a consequential acceptance decision requiring direct inspection, or an explicit human detailed-review request. This summary-first boundary reduces duplicated context without weakening coordinator synthesis, authority, acceptance, or critical-evidence requirements and uses no fixed size or round threshold.

Architecture evidence remains root-owned. Before confirming authority for architect consultation, the coordinator assembles the relevant existing packets and supporting locators and makes the evidence, pending decision, and value of specialist synthesis legible to the human. The architect may return one complete missing-evidence request or a batch whose units retain the same fields and mark dependencies and parallel safety. The coordinator checks every unit for materiality, duplication, accepted scope, read authority, and overlap with existing children; reuses applicable evidence; dispatches the smallest authorized root-owned gatherers concurrently for independent units and serially for dependent units; records them in the roster; and checks every packet. It surfaces the evidence in the main session and returns it within the same authorized engagement unless it creates a consequential unresolved choice or material change. When continuing, it resumes the same architect once with the relevant packets, session IDs, results, gaps, material delta, and exact critical evidence where details matter rather than once per gatherer. The transfer contract preserves critical evidence without replaying broad traces. The resulting design packet remains a human decision surface: the coordinator preserves its credible options, evidence and inferences, strongest cases and tradeoffs, recommendation, uncertainty and gaps, and reversal conditions until accepted under explicit current or prospective authority.

Requests requiring user direction, expanded access, mutation, reviewer judgment, or expanded scope stop at the coordinator's boundary. The architect neither delegates evidence work nor uses OpenCode session retrieval as a transport. This simpler topology remains preferred unless repeated live cases show material delay or primary-context bloat that outweighs shared evidence ownership.

The coordinator maintains a compact roster of child session IDs, roles, objectives, explored areas, latest reusable memory, and limitations. Each bounded `explore`, `research`, or `inspect` unit starts fresh by default, including related cross-role work. Resume is exceptional: a direct continuation of the same unresolved investigation and downstream decision, in the same role and materially overlapping evidence family, with no independence need and identifiable retained value that compact memory cannot preserve. Topic, repository, terminology, or role overlap alone is insufficient. Known context burden, staleness, compaction, noisy traces, failures, retries, and unrelated work favor freshness without becoming numeric thresholds; unavailable telemetry is neutral, prompt-cache economics are secondary, and routine routing never commissions session archaeology. Exact conversational or execution state may justify resume when these criteria otherwise pass.

Non-source continuity follows the context each role accumulates. `architect` and `ui-ux-designer` are strongly continuity-biased within one authorized downstream design engagement, including corrections, reframing, option refinement, checked evidence, explanation, and bounded extension. Disagreement does not end the engagement. Suspected anchoring first receives a correction-and-reconsider resume when still authorized; persistent anchoring may justify a separately authorized fresh independent opinion that supplements rather than erases the prior work. A materially new decision or system boundary starts fresh with new authority. An unavailable or unusable session may require replacement without changing authority for the same approved engagement. `triage` resumes within one symptom or incident and starts fresh for a different symptom, incident, environment, or independent diagnosis. `agent-author`, `prototype`, `operator`, and `worker` start fresh for each genuinely distinct accepted work unit. `artifact-author` starts fresh for each distinct artifact or coherent artifact set, resumes for feedback or correction on the same artifact and for an explicitly approved publication step in the same owning lifecycle, and starts fresh when audience, destination, artifact set, authority, or outcome materially changes. A clean stop on one bounded decision favors resuming when the user's answer preserves the underlying objective and artifact or work unit, relevant checkout context, sufficient authority, safely preserved state, and materially useful retained evidence or setup. A changed mechanism, provenance model, implementation route, or placement can remain the same unit when its old assumptions are explicitly corrected. Freshness applies when accepted outcome, primary ownership, artifact set, authority, system boundary, or validation contract makes the work distinct; when context is stale, overloaded, looping, or contaminated; after substantial preparation with no useful build continuity; or when independence is the purpose. Review findings normally define a fresh authorized remediation worker unit. `reviewer` and `pr-reviewer` start fresh for independent initial judgment and resume only to complete bounded evidence or conflict work within the same unconcluded review. After remediation, coordinator verification remains the default; a separately authorized independent rereview uses a fresh reviewer. Authority gates take precedence throughout.

These non-source defaults are provisional. Maintainers revise them from observed orchestration traces when the human explicitly asks for post-hoc assessment, not from generic expense labels, unavailable usage telemetry, or routine session archaeology during dispatch.

Durable OpenCode session history owns full traces and recovery. Task evidence notes preserve selected reusable findings rather than parallel session histories. The active compaction summary and current context are the default continuation path; compaction alone does not justify reconstruction. Work that genuinely starts after a deliberate manual compaction is a new phase and does not recover the prior phase. Work continuing across manual or automatic compaction first tests whether the active summary preserves the material decisions, evidence, child results, corrections, authority, and unresolved state it still needs.

When spanning work has a material continuity gap, the coordinator asks the root-owned `session-analyst` for the smallest reconstruction that crosses the relevant boundary. Multi-compaction recovery follows the relevant phase from its meaningful start rather than replaying the whole session or mechanically reading only one segment. The analyst returns a compact, decision-relevant packet; the coordinator treats it as evidence, checks it against active context, resolves conflicts or bounded gaps through focused follow-up, and incorporates it into the live working model. Persistent handoffs, Session Briefs, work-context checkpoints, OpenSpec artifacts, and similar records exist only through their separately requested owning workflows.

Coordinator verification is the normal acceptance path. After mutation, the coordinator checks the operator or worker report as evidence and performs focused acceptance verification for every affected repository or system. Git publication checks cover status, resulting commit identity, branch and upstream relation, and push state as applicable without repeating the operator's full investigation. After agent authoring, the coordinator inspects the changed artifacts, runs focused validation, reports uncertainty, and completes acceptance without recommending independent review. A reviewer remains available only when the user independently requests one. Child self-report never proves acceptance, and the agent that found or fixed a problem does not approve its own work.

At meaningful phase boundaries, the coordinator recommends one next step rather than presenting a generic menu. It classifies OpenSpec as recommended, optional, or not recommended after accepted design and asks before creating a proposal unless a concrete sequence already requested it. After implementation, the coordinator suggests independent review only for production changes with a concrete risk or verification gap that makes separate judgment useful. Production scope alone does not trigger a suggestion, and review never becomes a workflow completion or publication gate. Agent-author completion receives coordinator verification without a review recommendation. Recommendations do not expand authority.

## Success

One explicit command keeps conversation, shared evidence ownership, design, decisions, recommendation, acceptance, and child continuity in the user-selected primary context while specialists gather evidence and perform authorized work. Autonomous source gathering can establish readiness without silently advancing into specialist architecture synthesis. A concrete user request can authorize a bounded sequence up front, and the coordinator continues through conforming named steps without ceremonial approval turns while pausing visibly on material invalidation or unresolved consequential decisions. The human sees why architect consultation is useful, what evidence and decision it concerns, and the returned substantive design packet before acceptance or implementation under current explicit authority. Production-aware design compares credible staged and direct-cutover approaches on concrete constraints instead of treating production as an automatic mandate for transition machinery. External mutation uses proportional evidence, capable operator ownership, pre-change state capture, practical recovery, and verified resulting state without an automatic reviewer gate. Fresh source-gathering sessions avoid inherited trace burden while latest-only message memory preserves the bounded semantic context a related successor needs. Accepted implementation is decomposed into semantically coherent worker outcomes before conservative scheduling; sequential execution protects shared state, while proven-independent isolated work can realize material concurrency and return through an explicit integration boundary when needed. Compact evidence and memory flow back, architect-requested evidence remains reusable at the root, durable session history supports proportional targeted recovery when active context has a material gap, and bounded worker failures become checked triage evidence plus a clean continuation rather than a looping implementation trace. Bounded design questions can use authorized throwaway artifacts without becoming production work, accepted design can be recorded without broad reconstruction, substantial mechanical setup can be isolated from build context, and production implementation and independent review remain deliberate user decisions.

## Non-goals

- Creating planning artifacts without an explicit user request or bypassing their owning workflow.
- Delegating trivial coordination or restating the conversation through children.
- Making every task use every specialist.
- Automatic operator, worker, or reviewer dispatch without explicit user authority.
- Allowing the coordinator to implement when delegation is inconvenient.
- Acting as a neutral report aggregator without challenging, weighing, or recommending.
- Requiring OpenSpec, architecture delegation, or independent review for every change.
- Starting architect consultation merely because autonomous evidence gathering found a consequential design question.
- Manufacturing architecture alternatives when evidence supports only one viable design.
- Treating production context alone as evidence that compatibility layers, fallbacks, dual paths, or staged rollout are required, or presenting an irresponsible direct cutover as a nominal alternative.
- Routing ordinary application code or user documentation to `agent-author` merely because an agent may encounter it.
- Treating every file or every item called an artifact as `artifact-author` work, or routing application UI, throwaway prototypes, AI instructions, PRs, OpenSpec, or Jira work away from their owners.
- Treating prototype discussion, generic feasibility investigation, or a prototype result as authority to create, productionize, or publish code.
- Splitting trivial implementation setup into a ceremonial preparation phase.
- Splitting implementation mechanically by file, directory, repository, or arbitrary size count.
- Treating decomposition as a requirement to parallelize mutation or assuming different directories are independent.
- Creating worktrees automatically or parallelizing mutation while overlap remains unknown.
