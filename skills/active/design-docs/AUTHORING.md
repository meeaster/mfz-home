# design-docs

## Intent

Help a team reach and keep a concrete design for something that will be built or changed: take a large question (where to host new infrastructure, how to ship logs out of GovCloud), break it into decisions, questions, requirements, and evidence, carry it through meetings and emails, and publish a self-contained HTML design doc that a manager or a security reviewer can read on a shared screen. The records are the source of truth; the doc is built from them.

Not for: implementation plans or task lists, ADR-style records of decisions already made, general documentation, or publishing without a request.

Success: a new design looks and behaves like the bundled example without copying it; every diagram element cites evidence or an open question; meeting outcomes land exactly as agreed, with nothing stale left elsewhere in the doc; the build is one static file with no local paths.

## Scenarios

- **New design from a request and knowledge articles**: overview, areas where parts have their own records, briefs for decisions to weigh in a meeting.
- **After a meeting or an email thread**: proposes changes for the human to settle by number, applies what was accepted, then checks every page that mentions a changed ID or fact.
- **Hand the doc to a security team** (GovCloud, FIPS, CUI): each option has a security view with the compliance boundary, numbered flows, and where data rests.
- **Research open questions**: checks the knowledge base first, records evidence and answers directly, and considers what belongs in a knowledge article.
- **"What should we decide?"**: writes an AI recommendation labeled with the model that made it.
- **Fresh session picking up an existing design**: finds it through the effort's link, or the folder the user names, prepares a packet for its own task rather than reusing an earlier session's, and reads what the task needs.
- **Substantive change expands during discussion**: gathering maps impacts across the current design, updates affected packet domains, and preserves exploration versus acceptance before the author applies changes.
- **Evidence-heavy rewrite**: gathering by domain and an independent check keep the constraints that matter, so neither the writer nor one reviewer has to reconstruct the whole source pile, and the domains nobody could read are named.
- **Folder in an older format**: `check` refuses it and `migrate` converts it.
- **The direction changes the architecture**: freezes the current version, rewrites the design as the current state with records renumbered, and publishes the earlier version behind the version menu.
- **"Write the implementation plan"** or "make a task list": not this skill.

## Decisions

- **Records hold the facts; the agent writes only what's particular** (human, 2026-09-28 and 2026-09-29). JSON-driven rendering of whole pages was rejected first as too restrictive, because briefs differ too much. Pages then moved to Markdown plus records rendered by shared templates, so old docs regenerate when templates change. Diagrams stay free-form with no layout DSL, and any part can be a custom component. Reusable components exist to be reused where they fit, not to force a shape; improve a shared one only when other designs benefit too.
- **Records in JSON** (human, 2026-10-04). The human didn't want the skill telling models how to grep Markdown; give them a format they can read and edit directly. In comparison runs JSON was about as accurate as Markdown and Sonnet edited one record at a time naturally; the gain is structure, not cost. Figures used more than once are defined once as facts, which removed every stale-number failure.
- **Meeting changes are proposals the human settles before anything is applied** (human, 2026-10-05). One proposal per outcome the meeting settled, with an "Also records" line instead of one card per record touched; follow-on consistency fixes are proposed as record keeping; "Worth a look" holds judgment calls and is capped at three. Reaching 6–9 readable cards per meeting took three rounds.
- **A stale-text check runs after applying** (2026-10-05). Once proposals were reviewed before applying, nothing reviewed the finished pages, and hand-written diagram labels and prose went stale. Adding the check took acceptance runs from 27/30 to 30/30, at about $2.10 of Claude plan plus $0.62 of Sol per meeting.
- **Accuracy through maintained preparation** (human, 2026-10-20, revising the Oct 3 reading rule). Designs outgrew what one writer can read, and the writer is the expensive model. Broad changes can affect unexpected parts of a design; cheap gathering should cover all relevant material rather than leave it out to protect the writer's context. Substantive work starts with a scoped packet maintained through discussion, scope expansion and edits. Gathering runs on the cheapest models (Luna High), so the human first wanted a packet on every substantive change. A meeting-intake test on log-ingestion (Sol High writing, Luna High gathering, 2026-10-20) changed that: with and without a packet the proposals were equally good, but the packet run took 18.5 minutes against 3.2, with Sol reaching 162k tokens against 139k, because the writer still read design.json, meetings and references in full and then the packet on top. A packet pays only where it replaces the writer's reading, so it's for rewrites, designs built from many sources and recommendations across many decisions, and a meeting goes direct (human). Research is gathering, so it adds to a packet rather than waiting for one.
- **The writer reads an outline, not design.json** (human, 2026-10-20). design.json was the largest single read (43k tokens on log-ingestion, mostly question and decision explanations) and grows with every record. `doc.mjs outline` prints the prose and one line per record (about 4k there), and `show` prints named records in full, so a writer reads what the task touches and finds dependents by searching for IDs. The evidence is listed by its range only: at one line each it was 7k of the outline, and it's cited rather than read through.
- **Packet roles come from `roles`, for OpenCode** (human, 2026-10-20). "The user's routing" meant `role-models` (then named `orchestration-routing`): work routes explorers and inspectors to Luna High through the Tyler gateway, Personal through OpenAI. The playbook names the role for each step (explorer to gather and compile, inspector to check) with the task type `design-docs`, and lets `roles` pick the model; a task type rather than design-docs roles, so the system's own models apply only when this skill hands work out (human), which hands work out without starting orchestration. Only OpenCode matters: work runs there, and Claude Code runs on a personal subscription where cost isn't the constraint, so its routing wasn't added. Without `roles` the skill falls back to the cheapest capable model, since it has to work without Cairn.
- **One packet per session, outside the design** (human, 2026-10-20). A packet is gathered for the task in hand, and a later session usually works on something else, so it prepares its own. Keeping packets in the design folder, with `check` warning when one fell behind, was built and dropped for that reason. It's still written as files, in the session's working folder or a temporary directory, so it survives compaction and workers and the writer can read it.
- **Semantic preservation, not source indexing** (2026-10-20 pilot). A complete record-ID map still lost valuable routing modes, requirement authority, archive contracts and recovery constraints; a compiler also propagated a distribution/operator version error. Preserve the known constraints around open choices and check originals in bounded independent domains. The author can rely on checked packet findings; requiring all originals again defeats the handoff. Packet maintenance does not create another design authority or accept a proposed change.
- **Scripts for what every run reinvented** (2026-10-21). Transcripts of four runs on log-ingestion showed each run spending 15–25% of its carried context writing throwaway Node scripts to edit records by ID (7–11 per run, never the edit tool), 10–20% on repeated greps for IDs and phrases, and up to a quarter on one `show` of a dozen records that overflowed the harness's output limit and was read back in pieces. `set`, `refs` and a size-limited `show` replace those. A terser `show` format was measured and saved only 7%, so the JSON format stayed.
- **One skill with several page types** (human, 2026-09-28), renamed from `decision-brief`: overview, areas, briefs, and shared pages share components, cards, checker, and build, so separate skills would drift. Not every decision needs a brief.
- **A security view on every option** (human, 2026-09-28). The human hands these docs to a security team for GovCloud, FIPS, and CUI work.
- **Decisions carry Why, reasoning, Revisit if, and what else was considered** (human, 2026-09-29); decisions and questions carry an Explanation for readers who don't know why the item exists. Long detail opens in modals, not table rows.
- **Research needs no approval round** (human, 2026-10-06); it only gathers evidence. It starts by checking the knowledge base so research isn't repeated.
- **AI recommendations stand out and name the model** (human, 2026-10-06), shortly ("Opus", not a provider string), because recommendations differ by model.
- **The design owns the plan** (human, 2026-10-06). It isn't one-to-one with Jira; an effort only lists the Jira items related to it.
- **Which models do which step is orchestration, not skill content** (2026-10-05). At work, cost matters: Sonnet medium writing with Sol high reviewing matched Opus on accuracy in the comparison rounds. Put that split in agent definitions or session setup.
- **Less on the page, by progressive disclosure** (human, 2026-10-19). Readers can't keep track of D0, D1, E5; the log-ingestion doc showed long paragraphs, the same facts in several fields, and an ID every 25 words. Pages now show what a reader needs, each statement has one home, and detail opens from cards, marker lists and modals. Length isn't capped: the human rejected word counts, since some content needs more words; long text is broken into pieces a reader takes in one at a time (a few sentences, then bullets, a quote, a snippet, a number or a small diagram). `check` warns only on what's unambiguous: status narrated in prose and IDs written in brackets.
- **References named in words, with a coloured underline** (human, 2026-10-19). Mocked on the real doc against a tinted highlight and an underline plus a type icon: the highlight made dense paragraphs look marked up, and icons in a sentence break the reading flow. Evidence moves to one marker at the end of its paragraph or cell; in a table the marker sits at the end, never inline. Two or more chips, on a diagram box too, collapse into one counted button; the human accepted losing which decision a box carries at a glance, since IDs mean little to readers. The IDs switch brings them back for meetings. Markers and collapsing run in `doc.js`, so a doc without its script still shows every ID where it was written, and the switch can restore the page exactly.
- **Diagrams carry what they show** (human, 2026-10-19). A diagram is there so the reader doesn't have to read it as text, so the text beside it says only what the picture can't. Keys explain how things are drawn and leave out reference chips, which say what they are when clicked; the key component draws nothing for those entries, so older pages lose them without edits.
- **The author places, scripts check** (human, 2026-10-20). Layout is the model's job, guided by the skill and checked by looking; a script may apply a rule the guidance states (gathering a paragraph's evidence into its marker) but never decides where something goes. An automatic pass that guessed which box each diagram marker belonged to and moved it around text was built and dropped: its guesses were wrong often enough to show, and the model couldn't predict the page from what it wrote. Diagram markers are now one corner group per box, written by the author at the box's corner; `check` reports any that aren't, and screenshots catch overlap.
- **Snippets coloured with Shiki, bundled** (human, 2026-10-19). Long text breaks into pieces, and a snippet is one of them, so it should look professional, commands included. Prism (zero dependencies, has HCL) and Shiki were mocked side by side; the human chose Shiki as the better-maintained and more customisable base. It's bundled into `scripts/vendor` (core, the JavaScript regex engine, 14 grammars) so building a doc still needs nothing installed. Two things are ours: a theme whose colours are the doc's palette variables, so snippets follow light and dark, and command handling Shiki lacks: subcommands get their own colour, and a terminal session is split into prompt, command and output, since Shiki's shell-session grammar coloured none of the command in testing.
- **Editing passes as local draft changes** (human, 2026-10-19). Rewrites for brevity and duplication are shown side by side in a review copy before any reaches the design; they never publish. No accept or reject in the page: the human reads them and says what they think in chat. Meeting, email, evidence and voice-note updates stay on the update playbook, because they change what the design says. The page says "Changes"; the file is `.review/changes.json` so it isn't confused with `changes.md`. `apply-changes` refuses a rewrite that cites anything its text didn't, so an editing pass can't bring in a claim.
- **Working direction** (human, 2026-10-20). A design is open, working out what to do, or directed: an architect, a security review or the user has set the approach, and the design makes it work. Agents kept arguing with a direction the team had already been given, each problem turning into a proposed alternative; within a direction, a problem is a question or risk about it, and alternatives are a brief the user asks for. The human wanted only what the direction is and what it leaves open on the page, not who set it.
- **Versions, the latest written as if it were the first** (human, 2026-10-20). When the architecture changes (log ingestion moving to EKS in other accounts), the design is rewritten rather than amended. The human rejected a doc that explains what carried over: readers of the latest version shouldn't need the earlier one, and IDs may be renumbered, since nobody remembers them. Earlier versions are frozen with their published doc and open from a menu. Agents leave them unread unless the user asks about one, since loading an earlier version costs context on every design task and the current one stands alone (human).
- **Dark by default** (human, 2026-10-20). The doc opens dark whatever the system setting; the toggle still switches to light and remembers it.
- **What we're after names the real products** (human, 2026-10-20). The picture was first drawn generically ("Search and alerts", "Archive") so it wouldn't read as settled architecture; the human found that vaguer than useful and wants Datadog, AWS and the like named. It still stays above networks and accounts.
- **Terms open from the top bar** (human, 2026-10-20). A page's terms are read once, so the list under In short only pushed the page down, and on the EKS trial it ran to twenty entries. A Terms button in the top bar opens them in the record modal; without the script they still show under In short.
- **Static single-file output** for GitHub Pages or opening from disk; private links never reach the published file.
- **Scripts are Node only** (human, 2026-10-19). `doc.mjs`, `records.mjs` and the migrations were ported from Python and checked against it: every check, build, `--pages` build and migration produced the same output on the example, the template, two real designs, four older formats and six deliberately broken copies. The differences left are the parser's wording for invalid JSON and the embedded model's number format (`36` for `36.0`). The renderer is imported directly instead of run as a child process.
- **Works without Cairn, and cites the knowledge base only as provenance** (human, 2026-10-19). The skill moved out of Cairn's package so the team can use it alone. A design copies each claim it rests on, with when the article said it was observed, because articles keep changing and the published doc reaches readers without the knowledge base; the article's path is a `Knowledge base:` source that `check` resolves against a `knowledge/` folder beside the designs.
